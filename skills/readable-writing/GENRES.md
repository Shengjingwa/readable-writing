# 文体骨架

每种文体按下面的顺序写。这是内容顺序，不是模板：长文可以拿这些当小标题；短回复和短 MR 直接按顺序写成几句话，不加标题。某一项没有内容就跳过，下面写明要写「无」的除外。

## 报告 / report.md

1. 结论：这篇回答什么问题，答案是什么。
2. 依据：做了什么、看到什么。数字带底数。
3. 影响范围：哪些服务、哪些人、哪些环境。
4. 下一步：谁、做什么、何时。
5. 「待确认：」行。
6. 附录：命令、日志、哈希、链接。

## MR / PR 描述

整体写法：做到八成 ASD-STE100（航空维修手册用的受控英语规范）。借它的写法规则，不借它的词典。

1. 一句话：改了什么、为什么。关联 Issue 写 `Closes #12` 或 `相关：#12`。素材没给票号时，在「待确认：」行写明关联 Issue 待补。
2. 改动示意：改动跨 3 个以上模块，或改了调用关系、目录结构时，放一张最小示意；小改动跳过。从 diff 草图（用 `+` / `-` 标出新增和删除的结构）、调用树、文件树、Mermaid 里选最能说明问题的一种，只画和这次改动有关的节点。
3. 改动点：按模块或文件列。
4. 合入后的预期影响：会波及哪些调用方、用户和界面，以及迁移方式。素材能证明没有破坏性变更时，写「无破坏性变更」，并逐条列出依据，每条依据都要在素材里找得到；证明不了就写进「待确认：」行。
5. 验证：在什么环境、用什么命令。改了行为的，分别写改动前和改动后看到什么：失败和通过的测试、命令输出，界面改动优先放截图。纯重构写「前后输出一致」，并附比对命令。
6. 回滚：先写能不能撤回。删数据、改协议、对外发布这类撤不回的改动，用「注意：」开头单独成句。能撤回的写怎么回滚；预案没定就写进「待确认：」行。
7. 「待确认：」行：没验证的环境、缺的步骤。
8. 机器字段（`Change-Record` 等）照原样放在末尾。

## 同事回复 / 指派人回复（IM）

1. 第一句：直接回答对方的问题，或给出现在的状态。
2. 依据：1 到 3 句，只放对方要核对的事实。
3. 请求：需要对方做事时，最后一行写请谁、做什么、何时需要。

按 IM 消息写：不用小标题，不加粗分节，整条控制在一屏内。分支名、路径、哈希、链接放在最后一行，一个不删。

## 工作纪要

1. 决定：每条写决定了什么、谁拍的板。
2. 待办：每条写负责人、事项、截止日期（绝对日期）。
3. 未决问题：每条一行「待确认：」，写清卡在哪、等谁。
4. 讨论要点：可选，只记影响决定的分歧。

## 故障通报

1. 现状：现在恢复了没有、用户还受不受影响、要不要担心。
2. 影响：哪些服务、多少请求或用户（带底数）、起止时间（绝对时间，跨时区加时区）。
3. 处置时间线：每条写时间、谁、做了什么、结果。
4. 原因：只写已坐实的。没坐实的写进「待确认：」行。
5. 下一步：谁、做什么、何时。
6. 故障还没结束时，末行写「下次更新：<时间>」。

## 讲解（给没有背景的同事解释概念）

整体写法：做到八成 ASD-STE100（航空维修手册用的受控英语规范）。借它的写法规则，不借它的词典。

1. 第一句：它是什么、解决什么问题。
2. 一个例子：素材里有比喻或真实案例，就用素材的。素材没有，再选读者熟悉的场景假设一个，并写明「假设」。用类比时，写明类比和实际不一样的地方。
3. 怎么工作：分步骤，每步一句。涉及 3 个以上节点时按配图规则配图。
4. 和读者的关系：读者什么时候会碰到它、要注意什么。

每个新术语先讲清它是什么，后面再用它。素材里出现的组件、仓库、运行位置都要讲到。只把有出处的事写成真实发生过的事。
