# 人话写作

读者是同事，不是这份代码的作者。报告、MR、回复、纪要、说明都按这个写。

贴进来的代码、日志、命令、配置，一个字都不要改。里面有 token、密码、私钥、证书、手机号身份证等敏感信息：整段或该串替换为打码占位（如 `***`），并在块外紧邻处注明「已脱敏」，其余照旧不改。看不出敏不敏感的整段先不贴，在「待确认：」行注明疑似敏感内容未贴，严禁将原值写入待确认行。

## 先把事说清楚

1. **先结论。** 开头一句先写读者最想知道的事。刚上线、出过故障、刚回滚：写现在怎样、该不该担心、下一步做什么。现在怎样还没坐实：首句写清已经发生了什么、状态尚未验证、下一步做什么，未坐实项指引下方「待确认：」行。没有这些情况：写这篇要回答的问题，以及你的答案。细节和哈希放到后面。
2. **写动作和结果。** 谁做了什么、改了什么、看到什么。
3. **名字照留，说法翻译。** 仓库、tracker、日志、看板里搜得到的名字，用原名：代码符号、接口名、命令、配置项、分支名、环境名、tracker 标签。第一次出现时，同一句写清它干什么。搜不到的说法（实验代号、口头简称）翻成它指的那件事。必须用的术语保留原词，第一次出现时用括号补一句它是什么。词义冲突按优先级裁决：搜得到的符号与专名保留原名 > 中文在同句说清业务含义 > 口头简称必须翻译所指，不单用简称。后文需稳定简称，首次写「全称（下文简称 X）」后全文用 X。关联 Issue 或卡片时按原名引用：自动关票用 `Closes / Fixes #12`，仅供参考写 `相关：#12`，票号缺失记入「待确认：」。
4. **数字带单位和底数。** 耗时、次数、比例，写清是什么的多少。例如 `P95 820ms`、`50 次请求里 14 次超 1s`。可计数的发生比例必须给底数：写 `14/50`，不要只写 `0.28`；此类底数拿不到时，写明拿不到并放到「待确认：」那一行。无离散采样分母的原生百分比指标（如 CPU、内存、SLO 达成率）不用强拆底数，写清所属服务、时间窗口与统计口径（例如 `订单服务 10:00-10:30 CPU 均值 62%`）。表头用中文。表前面加一句话，说明每列是什么。
5. **没坐实的另起一行，没有的不补。** 没部署、没验证、只是近似对照、读数对不上：从结论句里拿出来，单独起一行。行首写「待确认：」，写清哪一条还没坐实。多项没坐实时，每项单独起一行「待确认：」，或在「待确认：」下一并列出清单；结论句只写已坐实部分，指引下方待确认。diff、日志、聊天记录、看板里没有的数字、原因、责任人，不要补。「待确认：」行里已经有的数字，原样抄，不要改精度。
6. **机器字段照留。** `Change-Record` 这类字段保持原样。正文用中文写改了什么、为什么。刚上线、出过故障、刚回滚时，再写线上现在怎样。未合入的 MR 描述：写预期合入影响、受影响用法与迁移方式（无破坏写「无破坏性变更」）、在何环境用什么命令/操作验证且看到什么期望结果；没验证或回滚预案未定时，在「待确认：」行写明缺哪一步。

## 别演写作

- 空话划掉。划掉以后事实还在，就划掉。例如：赋能、打造、显著提升、有效改善、底层逻辑、值得注意的是、在当今……时代、接下来我将、不容忽视。第几段出现都划。上面只是例子。
- 主语要指得到某个人或某个服务。动词后面要跟得上看得见的结果。「我们深入思考了」「接下来稳稳兜住」两样都没有。「重试 3 次后仍返回 502」两样都有。
- 同一件事从头到尾用同一个词。
- 有对比，直接说哪边更要紧。
- 问什么答什么，答完就停。短回复不要再加一段收尾。说明不要寒暄、不要铺垫。需要对方行动（求评审、求拍板、指派跟进）时，最后一行写清请谁、做什么、何时需要。
- 写别人能核对的事实。把「你可能担心兼容性」换成「兼容性只在 `staging` 验过」。
- 一个短语如果顶掉了好几步动作，把那几步分开写。`red-green` 这类别处已经有的名字可以照写；要别人照着做时，那几步单独列出来。
- 停笔前自检四项：首句是否回答读者最关心的事、每个动作是否看得见结果或标明待确认、比例是否带底数、无冗余收尾与未点名的套话。

```
（写动作和结果 · 先结论）
❌ 本次优化显著提升了系统整体性能，并有效改善了用户体验。
✅ 订单服务现在的接口耗时正常，不用回滚。我在 staging 跑了 50 次请求压测，P95 从 800ms 降到 120ms，改的是查询链路。

（名字照留，说法翻译；末行示范「待确认：」怎么写）
❌ 清雾后再切票。绿场。仓库越改越泥。
✅ 这轮只做两件事：把要拍板的事写下来，再拆成一次能做完的任务。
待确认：方向还没定。
```

某次任务里临时起的叫法，不要写进这份规范。先把事情讲明白，不要另造一套词。
