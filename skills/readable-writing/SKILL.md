# 人话写作

读者是同事，不是这份代码的作者。他读一遍就能行动，不用回头追问。报告、MR、回复、纪要、讲解都按这个写。

按任务读对应文件：

- 从头写：先读 [GENRES.md](GENRES.md) 里对应文体的内容顺序。
- 改写别人给的文字：先读 [REWRITE.md](REWRITE.md)。
- 写英文：句子规则换成 [ENGLISH.md](ENGLISH.md)，其余照本文件。
- 交出去之前：读 [CHECKLIST.md](CHECKLIST.md)，逐条对照修改，全部通过才交。

## 底线

- 作为证据引用的代码、日志、命令、配置、标识符、路径、数字、引文，一个字都不改。这条只管引用；实际改文件仍按用户的任务授权执行。
- 敏感信息打码：token、密码、私钥、证书、手机号等，把敏感串换成 `***`，在块外紧邻处写明「已脱敏」，其余照留不改。看不准敏不敏感的整段先不贴，在「待确认：」行写明有疑似敏感内容未贴，严禁把原值抄进待确认行。
- 缩短句子时，事实、条件、例外、适用范围全部保留。
- 定位信息（分支名、路径、哈希、链接、run ID）一个不删；嫌长就挪到末尾。
- 不确定的事保持不确定：「可能」「计划」照写，或移到「待确认：」行。

## 先把事说清楚

1. **先结论。** 开头一句先写读者最想知道的事。细节和哈希放到后面。
   - 刚上线、出过故障、刚回滚：写现在怎样、该不该担心、下一步做什么。
   - 状态还没坐实：写清发生了什么、状态尚未验证、下一步做什么，并指出看「待确认：」行。
   - 其他情况：写这篇要回答的问题，以及你的答案。
   - 首句概括多项时，每一项都要成立。有一项不成立，就把它单独拿出来说。
2. **写动作和结果。** 谁做了什么、改了什么、看到什么。
3. **名字照留，说法翻译。**
   - 仓库、tracker、日志、看板里搜得到的名字用原名：代码符号、接口名、命令、配置项、分支名、环境名、tracker 标签。第一次出现时，同一句写清它干什么。
   - 搜不到的说法（实验代号、口头简称）翻成它指的那件事。
   - 必须用的术语保留原词，第一次出现时用括号补一句它是什么。
   - 撞名时按顺序：能搜到的专名用原名；同句用中文讲清业务意思；搜不到的口头简称翻成它指的事。
   - 后文需要稳定简称：第一次写「全称（下文简称 X）」，后面统一用 X。
   - 关联 Issue 或看板卡片按原名引用：自动关票写 `Closes / Fixes #12`，仅供参考写 `相关：#12`。素材提到了 Issue 却没给票号时，记入「待确认：」行。MR 描述另有规定，见 [GENRES.md](GENRES.md)。
4. **数字带单位和底数，时间写绝对日期。**
   - 耗时、次数、比例写清是什么的多少，例如 `P95 820ms`、`50 次请求里 14 次超 1s`。
   - 数得出来的比例给底数：写 `14/50`，不只写 `0.28`。底数拿不到时写明拿不到，放进「待确认：」行。
   - 监控里直接读出的百分比（CPU、内存、SLO 达成率）不用拆底数，写清所属服务、时间窗口和统计口径，如 `订单服务 10:00-10:30 CPU 均值 62%`。
   - 时间写成 `2026-10-08 10:30` 这样的绝对日期；读者跨时区时加时区。「昨天」「上周」换成日期。
   - 表头用中文。表前面加一句话，说明每列是什么。
5. **没坐实的另起一行，没有的不补。**
   - 没部署、没验证、只是近似对照、读数对不上：从结论句里拿出来，单独起一行，行首写「待确认：」，写清哪一条还没坐实。
   - 多项没坐实：在「待确认：」下列清单，每项一条。结论句只写已坐实部分，并指出看下方待确认。
   - 「待确认：」只放还没坐实的事。已经确定的限制（例如「这轮对照是近似」）写进正文。
   - 「待确认：」只标记事实没坐实，不是停工信号。只有这件事决定安全或范围、不坐实就没法往下做时，才停下来问；不依赖它的工作照常做。
   - diff、日志、聊天记录、看板里没有的数字、原因、责任人，不补。
   - 「待确认：」行里引用的数字原样抄，不改精度。
6. **机器字段照留。** `Change-Record` 这类字段保持原样，正文用中文写改了什么、为什么。MR 描述的内容顺序见 [GENRES.md](GENRES.md)。

## 句子怎么写

1. **一句一件事。** 操作步骤一句不超过 30 字，叙述一句不超过 50 字，超了就拆。代码标识符、数字连单位各算 1 字。拆开会丢条件时，保留长句。
2. **一段一个话题。** 一段不超过 6 句。
3. **一词一义。** 同一件事从头到尾用同一个词；一个词全文只指一件事。「验证」指跑测试，就别再拿它指人工评审。
4. **主动句。** 写清谁做的：「运维改了配置，再重启订单服务」。不知道是谁做的时候才用「被」。
5. **成分写全。** 主语、动词、宾语都在：「没备份的配置文件会丢失」，而不是「未备份的会丢失」。
6. **定语不超过 3 层。** 一个名词前面挂的修饰（「的」字链、名词堆叠）最多 3 层。多了就拆成两句，或先给它起名再用。
7. **警告放句首。** 风险、前提、不可逆操作单独成句，用「注意：」开头。
8. **3 项以上用编号。** 3 步及以上的操作、3 个及以上的并列条件，用编号列表。
9. **用实在的动词。** 写「优化了查询」「验证配置」，动作直接做谓语，「进行」「实现」「做出」这类空动词换掉。

为了读着顺，两个相关的短句可以用「并」「如果」连成一句，前提是每半句仍只有一个动作或判断。

## 配图

讲流程、调用链、状态变化，且涉及 3 个以上节点时，配一张图：Mermaid，或文本示意（diff 草图、调用树、文件树）。结论句写在图前，再用一句话说明图里看什么。只在能渲染 Markdown 的地方配图：MR、report.md、文档。IM 回复（企业微信、飞书等）改用编号步骤。

## 写事实，不写姿态

- 每句话写出主语、动作和看得见的结果，主语是某个人或某个服务。「重试 3 次后仍返回 502」就是这样的句子。删掉一句后事实一个没少，就删掉它。
- 素材给了轻重，就直接说哪边更要紧。自己的判断（排轻重、建议、推断）单独起一行，行首写「我的判断：」，和事实分开。
- 第一句就进正题，问什么答什么，答完就停。需要对方行动时（求评审、求拍板、指派跟进），最后一行写清请谁、做什么、何时需要。
- 写别人能核对的事实，例如「兼容性只在 `staging` 验过」。
- 一个短语顶掉了好几步动作，就把几步分开写。`red-green` 这类别处已有的名字可以照写；要别人照着做时，几步单独列出来。

```
（写动作和结果 · 先结论）
❌ 本次优化显著提升了系统整体性能，并有效改善了用户体验。
✅ 订单服务现在的接口耗时正常，不用回滚。我在 staging 跑了 50 次请求压测，P95 从 800ms 降到 120ms，改的是查询链路。

（一句一件事 · 主动句 · 定语不超过 3 层）
❌ 在对配置文件进行修改并被重启之后的订单服务的超时问题已经得到了解决。
✅ 运维改了配置文件，再重启了订单服务。之后 200 次请求里 0 次超时。

（名字照留，说法翻译；末行示范「待确认：」怎么写）
❌ 清雾后再切票。绿场。仓库越改越泥。
✅ 这轮只做两件事：把要拍板的事写下来，再拆成一次能做完的任务。
待确认：方向还没定。
```

某次任务里临时起的叫法，不要写进这份规范。先把事情讲明白，不要另造一套词。
